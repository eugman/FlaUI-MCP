# Known issues

## Clearing the Preferences search blanks the settings pane

Seen in TE3 3.26.3.12966. Clearing the Preferences search box, with its × button or by deleting the text, blanks the settings pane. It does this even when you chose the category from the tree and the search box was already empty. The category stays highlighted.

Workaround: after any change to the search text, click the category again. That brings its settings back.

## Clicking a container can hit a child control

A click on the centre of a pane, made just to focus it, once toggled the "Always prefix extension columns" checkbox. Native-window hit checks prove which window was hit, not which UIA child.

Workaround: don't click pane centres to focus them. Focus a known focusable control instead.

## Dragging the shared edge of touching panes undocks the lower pane

Seen in TE3 3.27.1 at 125%. TOM Explorer and Properties touch with no gap. A drag that starts on the shared edge grabs the Properties title bar, and Properties became a floating `Properties` window. The splitter is in the upper pane's last few rows.

Changed in the host: `te3_layout resize` starts the drag 3 px inside the upper or left pane when two dock panes touch or are at most 2 px apart, and fails with `undocked: true` and a next action when a new titled window of the TE3 process appears after the drag. Each drag also passes the other panes' captions and the document tabs as Core's `windows_mouse` `fromMustNotHit`, so a start that UI Automation places on one of them is refused before the button goes down. Verified live on te3-eb2ed6a (2026-10-22), window restored at (0,0,1920,1080): `resize` TOM Explorer 467 -> 480 in 1 attempt, 15 inputs and 5.2 s with the drag starting 3 px inside TOM Explorer, (1404,374)->(1391,374); `apply-preset assistant-model-review` moved AI Assistant 663 -> 680 with the drag (660,534)->(677,534) (15 inputs, 5.3 s) and skipped TOM Explorer and Properties, already at 480/320, with 0 inputs. Both starts passed `fromMustNotHit`, which now includes the pane's own caption, and nothing undocked. The host does not check that the pointer is on the splitter itself (the resize cursor shape is not read). Fixed offline, not yet run live (9809dc8, 85b2073): the 3 px inset and the 5 px splitter offset are device-independent pixels (2 and 3 at 96 DPI) scaled by the TE3 window's DPI, so they read 3 and 4 at 125% and 4 and 5 at 175%; of these only the inset 3 at 125% and the offset 5 at 175% were seen live, the offset 4 at 125% and the inset 4 at 175% are arithmetic a live run must verify (a resize at each scale, with no undock); the pane bounds and the window origin are read in one pass, the origin before and after, and the drag is refused when the window moved between the two reads.

## Show changes hides everything else in TOM Explorer

Seen in TE3 3.27.1. With the TOM Explorer `Show changes` filter on and no unsaved changes, the tree is empty and the title reads `TOM Explorer (Changed)`. Object navigation then reports that the table is missing.

Fixed in the host: `te3_navigate object` turns Show changes off before it walks, and reports "show-changes filter active" with a next action if it stays on. Verified live.

Closed gap: `te3_navigate` `tom-explorer/changes-off` turns the TOM Explorer filter off on its own (the CheckBox, polled until it reads off, then checked on arrival). Verified live on te3-cfa803c (2026-10-21) with `tom-explorer/changes` (title `TOM Explorer (Changed)`, then `TOM Explorer`; 1 input each). Turning it off drops the TOM Explorer selection to "(Nothing selected)": the host does not restore it, so navigate to the object again afterwards if the shot needs it. Earlier the filter was turned off in a live session with a raw Toggle on the CheckBox, which dropped the TOM Explorer selection. Properties' own Show changes has no bindable command and no host tool; the TOM Explorer one is bindable as `TomExplorer.ToggleChangedOnly`.

## Object navigation can outrun the 30-second tool deadline

Seen in TE3 3.27.1 on SpaceParts. Navigating to `Brands[Brand]` walks the filtered tree with Down presses. With and without `folder` (`1. Brand Hierarchy`), the walk was cancelled at the 30-second deadline after 15 inputs, leaving another row selected (`Table "Products"`).

The deadline is Core's fixed 30 s per tool call (`ToolRegistry`); a broker `--timeout` does not lift it, and this host cannot change it. The walk now stops itself once 18 s have passed since the tool call started (opening TOM Explorer, the Show changes check and the typed search count), which leaves about 6 s to clear the search, and fails with the rows visited, the inputs sent, the row it stopped on and its table, instead of being cancelled mid-key. Each Down waits at most 1.5 s, reads included. The earlier 20 s stop, counted from the start of the walk, was verified live. The 18 s total-time stop was verified live on 2026-10-21: without `folder` the walk stopped itself after 8 rows and 16 inputs, cleared the search and reported the row it stopped on. With `folder: "1. Brand Hierarchy"` it reached `Brands[Brand]` in 16.7 s and 13 inputs. The host ignored `folder` then, so that success came from a faster walk, not from the argument: whether this column is reached depends on walk speed against the 18 s stop, and the clock leaves little headroom. `folder` is now honoured (the object must be inside it, and the walk stops once it leaves the table), which gives a precise reason on a miss but no speed; not yet run live. A Down that does not move within 1.5 s while a row is shown below the selection is now reported as a slow tree, not as the end of the tree. That check sees only the rows UI Automation has realized, and at most the first 200 TreeItems the selection read returns: when the selection is the last realized row (at the bottom edge of the pane, or past row 200 of a long tree), a slow Down is still reported as the end of the tree. A deep object can still be out of reach; raising the limit needs a Core change. After a failure, observe the selection with `te3_model_state`. Don't retry blindly.

On te3-eb2ed6a (2026-10-22) no walk came near the clock: the row strategy took 5.7-9.8 s, the `rows-by-table` fallback 12.0 s and the keyboard fallback 23.2 s (it stopped itself before the deadline). See "Object walk timing" below for what failed instead.

## Filling the Scintilla editors without a focus check

The expression editor and the DAX query editor are Scintilla controls (`daxscilla`). Whether UI Automation reports keyboard focus on the control itself, or on a child, was never checked live.

Changed in the host: both fills now pass Core's `verifyFocus: "self-or-descendant"` (Core c807de5), so the keyboard fallback refuses before Ctrl+A unless focus is on the editor or inside it.

Seen live on te3-eb2ed6a (2026-10-22), so this row is closed: the expression editor's `daxscilla` Pane (class `WindowsForms10.Scintilla.app.0.1e2bef7_r3_ad1`) reports keyboard focus on itself. With focus in TOM Explorer, `windows_send_keys` with the editor's ref and `verifyFocus: "self-or-descendant"` did not refuse: Core focuses the ref first (counted as an input: `[End]` cost inputsSent 2) and the check then saw focus on the control itself. After `te3_navigate expression-editor` (1 input) the control read `keyboardFocus: true` and `[Ctrl+End, x, Backspace]` went in with inputsSent 3 and the expression read back unchanged (the DaxEditor Pane's name is the expression text). The refusal case is therefore a control that cannot take focus, not one that is merely unfocused: a TOM Explorer TreeItem is such a control (`Ctrl+Z` through a row ref was refused with `focus-not-verified`, 0 inputs). Neither `daxscilla` nor `DaxEditor` is realized while the editor shows `(No DAX properties)`: select a measure first.

## The runner's activation click is checked by position only

When Windows refuses to bring the runner's TE3 forward, the run continues only after a mouse click whose point lies inside TE3's window rectangle (and no typing). The rule is Core's now (`InteractionGrant.BeginPrompt`, then `Rebaseline(bounds)` at the first 250 ms poll that sees TE3 in front, applied atomically, with a 120 s prompt window), and it is still by position: a click on another window that overlaps TE3's rectangle, followed by TE3 coming forward, is accepted as the go-ahead. Core's adapting notes do not hit-test the activation click (the click is in the past when TE3 comes forward, so a hit test now would read the window that is in front now, not the one clicked); a fix needs the observer to record the window under each button-down, a Core change.

## Closing TE3 needs an active interaction

`windows_close` on the TE3 window is a desktop change like any other, so it is refused (not-dispatched, 0 inputs) after `te3_interaction_end`. The host keeps it that way rather than exempting its own close: end the interaction only after TE3 is closed, or begin a new one for the teardown (te3-6535504 did the latter). `te3_layout restore` needs no interaction, so it can run after the end. Done that way on te3-eb2ed6a (2026-10-22): `windows_close` before the end (1 input, no prompt with a clean model), `te3_interaction_end`, then `restore` with TE3 closed put the three files back and read the snapshot's hashes.
