# Changelog

Changes to the Tabular Editor 3 tools and runner. Changes to the generic `windows_*` server are in the
[FlaUI-MCP-Core changelog](https://github.com/eugman/FlaUI-MCP-Core/blob/main/CHANGELOG.md).

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/).

## [Unreleased]

### Changed
- `te3_layout restore` first copies the layout files it is about to replace into a snapshot of their own beside the one restored (`<name>.replaced-<time>`, returned as `replaced`); restoring that folder undoes the restore. A restore that stops part-way no longer leaves a `.tmp` file, and its error names that folder.
- **Breaking:** `te3_native_preflight` accepts a `tokenEnv` only when its name starts with `FLAUI_TE3_` (for example `FLAUI_TE3_MCP_TOKEN`); any other variable is refused before a request is made, so a caller cannot have another service's token sent to a loopback listener. Rename the variable that holds TE3's MCP access token.
- The run manifest has `settingsBackupRemoved`: true once the backup `settingsBackup` names was removed after a verified restore, by the run or by `recover`.
- A run whose TE3 did not exit on its close request and had to be killed says so in the manifest's `diagnosticNotes`.
- A failed run notes only a real revocation it saw: input after a normal end (`after-end`, still in the interaction reply) and a revocation from before the run started are not added to its `diagnosticNotes`.
- How the grant ended reaches the run and the agent: a failed run adds `InteractionGrant.LastRevocation`'s one-line summary to its manifest `diagnosticNotes` (not for the run's own normal end), and `te3_interaction_begin`/`te3_interaction_end` reply with `lastRevocation` beside `active`. `Te3Interaction.LastRevocation` exposes it.
- A settled Core call that failed before any input without its own refusal now becomes a typed `tool-failed` TE3 result with `actionDispatched: false`. Wrapping an inner failure preserves `actionDispatched: true` even if the outer TE3 input tally is zero, and that evidence pauses the interaction grant until observation. A Core `partial` or `completed` failure with no counted input also stays dispatched and cannot be retried; a Core call is retryable only with an explicit zero input count, `not-dispatched`, and no contrary failure evidence.
- Keys sent to the Scintilla editors (the query editor's F5) ask Core for `verifyFocus: "self-or-descendant"` explicitly instead of relying on Core's default.
- The run's click prompt is ended with `activation-denied` whenever the wait for the click fails (timeout, cancellation, TE3 exiting, a second TE3, no window bounds), before the run's capture and cleanup.
- The waits in `Absence` and the object walk's `AwaitMove` stop on a poll count as well as the clock, so a clock that does not move cannot hold them; the popup captures poll for the popup (`SettlePoll`) instead of one read after a fixed 500 ms.
- A dialog cancel the grant or the desktop refused is reported at once with its code instead of trying the next button and timing out.
- The Show changes gate refuses (not-found) when the checkbox vanishes after its click, instead of taking that for "off"; an IsOffscreen that cannot be read is unknown, never "on screen", so the TOM Explorer tab is then required.
- The dialog an action opened is matched by owner (TE3's main window first) and dialog class, several candidates are refused, and a cloaked window is reported as cloaked, not closed; `OpenPreferences` waits for a Preferences window opened since a window baseline.
- The BPA tab is read back after `OpenBpa`; the script run, Save and New query are recorded as unverified (`UnverifiedSteps`).
- `recover` takes its runner lock, settings directory and TE3 process list through seams, so its tests never touch the real lock or live TE3s.
- `te3_navigate object` returns its `walk` account as a top-level `structuredContent` field (Core's `ToolOutcome.Details`, merged at c9e94b8), on success and failure; the message text no longer carries it.
- **Breaking (codes):** the grant's refusal codes are Core's hyphenated ones: `approval-required`, `focus-revoked`, `focus-unavailable`, `paused-after-failure`, `activation-denied`, `activation-pending`. Map old underscore spellings with `RefusalCodes.Canonical`.
- Rebased on FlaUI-MCP-Core 84280c0. `Te3Interaction` is built on Core's `InteractionGrant`; TE3's own input observer, heartbeat and grant are gone. The run's activation prompt uses `BeginPrompt` then `Rebaseline(bounds)`; constructing the grant makes the host fail closed on a path without it (`MutationGuard.HookRequired`). The input lease is Core's machine-wide mutex; the offline tests take a lease of their own process.
- A `windows_*` call that fails after sending input now pauses the grant, as a failed TE3 tool does (Core's `ToolRegistry.FailedAfterInput`).
- `CoreCallException` is one of Core's refusals (`AutomationRefusal`, with `Code`, `InputsSent`, `Disposition`), not an `InvalidOperationException`; polls catch only not-found, so a refusal is never relabelled as a timeout.
- Successful `te3_navigate`, `te3_layout`, and interaction tool replies carry Core's `proof` from their read-back: navigation by the selection TE3 names (object) or the arrival check, layout by the panes, button, size, tabs or file hashes it reads back (no-op when nothing needed doing), and the interaction tools by the grant's state. A failed action may have sent input and report dispatch/refusal evidence without a proof. `PlacementReadBack` reads Core's `placement-mismatch` code.
- The TE3 tools carry Core's tool facts (`observationHint` for `te3_model_state` and `te3_layout_read`, `recoveryHint` for the interaction tools and `te3_env_check`); their table in automation/README.md is generated from them, and `Te3ToolNames` lists the tools once.
- The expression and query editors are filled with Core's `verifyFocus: "self-or-descendant"` instead of no focus check.
- `te3_layout resize` and `apply-preset` drags pass the neighbouring captions and tabs as `windows_mouse` `fromMustNotHit`.
- `te3_navigate object`: arrival after the search clears is judged by the selection's identity; an object already selected costs no keys and no select; when the name search places no candidate, the tree is filtered by the table's name and the object looked for under it (`walk.strategy` `rows-by-table`); a miss never says "table 'none'" and its `walk.objectType` is the requested type.
- **Breaking:** `te3_layout`'s read-only actions (`list`, `show-pane`, `plan-preset`) moved to the new `te3_layout_read`, so each tool has one MCP annotation (`te3_layout_read` read-only, `te3_layout` destructive). `te3_layout` refuses them and names `te3_layout_read`; callers that list panes or plan a preset must call the new tool. Every TE3 tool now declares annotations.
- `FlaUI.Mcp.Te3 mcp` is now the one server to configure. It serves the generic `windows_*` tools (including the window-management extensions) alongside the TE3 tools from one registry, so element refs and window handles work across both. Running `FlaUI.Mcp.exe` next to it is no longer needed.
- A failed `te3_navigate` or `te3_layout` call reports how much input went out the way Core's tools do, in `structuredContent`: `dispatch` (`partial`, `not-dispatched`, or `timed_out_pending` while the failing call may still go out), `inputsSent`, `provider` and the refusal as `failure`. The `actionDispatched` and `inputsSent` fields are no longer in the text. A held TE3 provider is reported as Core's blocked outcome (`not-dispatched`, `provider: pending`).
- TE3 counts input from Core's `inputsSent`, including the activation and focus Core counts, and reads refusals, retries and cancel fallbacks from Core's outcome instead of matching "no input sent" in the text. `te3_navigate` names `activation-denied` and `desktop-unavailable` blockers from the refusal's code.
- The TE3 server serves Core's own `windows_focus`, `windows_close` and `windows_launch`, which now check the grant themselves; the TE3 wrappers, which had replaced Core's tools with ones built without the pending tracker, are gone. The runner focuses its TE3 through Core's guarded focus and counts it, and refuses first while an earlier call still holds TE3's provider. Core's focus by native handle deliberately bypasses the pending tracker (it is how a blocking modal is reached), so the runner checks the tracker itself, as Core's adaptation notes recommend.
- Te3Page's own menu clicks go through `GuardedInput.Click` and Core's `ClickPoint`; a covered pointer target is refused as `point-not-on-target`.
- The run journal's result entries carry `isError`, `content` and `structuredContent` explicitly.
- The TE3 offline tests set `FLAUI_OFFLINE_TESTS=1` and install a fake desktop, so the real desktop refuses input from them.
- The TE CLI starts through Core's `GuardedDesktop.StartProcess`.
- TE3 coverage and mutation testing moved to `scripts/coverage-te3.ps1` and `docs/mutation-te3.md`; `scripts/coverage.ps1`, `scripts/mutation.ps1` and `docs/mutation.md` now belong to the core and cover its own offline tests. `dotnet-stryker` comes from the core's root tool manifest.
- `ToolRegistry.ResolveTarget` (arguments only) is removed; `ResolveTargetForTool` (tool name and arguments) is the one target resolver, and `RegisterAllToolsInto` composes a host's with Core's as before. No host project set the old one. `FailedAfterInput` stays beside `FailedAfterInputWithTarget`: the Power BI and Camtasia hosts set it. A call and a batch step now share one setup of target, permission hook and advisory. The tools' own waits (hover, drag steps, key pauses, read-back polls, the window-state settle) go through `InputDesktop.Pause` and `Time`. Fixed offline 2026-11-10, not live-verified.
- A `windows_launch` that attached a provisional window no longer carries `failure: {code: launch-provisional}` on its successful reply; it says `provisional: true` in its details (top level of `structuredContent`) beside `processId` and `windowHandle`. `status: unverified` and `verification: provisional-window` are unchanged. The code `launch-provisional` is no longer emitted. Fixed offline 2026-11-10, not live-verified.
- `initialize` reports `serverInfo.version` from the core assembly's version (0.2.0 now) instead of a hard-coded 0.1.0.
- An unknown JSON-RPC method is answered with -32601 (Method not found) instead of -32603; the message `Unknown method: x` is unchanged, and -32603 stays for a request that fails in the server.
- `windows_screenshot` validates `savePath` with `HostPath.Validate`, the rules a host's configured paths follow: the forward-slash UNC form (`//server/share/x.png`) passed the old prefix test and a capture could be written to a network share. A `savePath` with `.`/`..` segments, `~`, or a segment that starts with `$NAME` or `${NAME}` is now refused; a defined `%NAME%` is expanded. Any other `$`, and a `%NAME%` that is not defined, stay as written (a host's configured paths keep the stricter rule). Fixed offline 2026-11-10, not live-verified.
- `windows_click`'s mouse click releases the machine-wide input lease right after the click, before it observes the selection or waits up to 2 s for the dialog a "…" item opens; that wait polls through the desktop seam. Fixed offline 2026-11-10, not live-verified.
- `windows_paste` releases the machine-wide input lease right after Ctrl+V, before its read-back polls the value for up to 2 s, and reads the value and waits through the desktop seam (`InputDesktop.ValueOf`, `Time`, `Pause`). A password field's value is no longer read back into `proof.observed`; such a paste is `unavailable`. Fixed offline 2026-11-10, not live-verified.
- `InteractionGrant.Launch` runs its launch delegate, and `Begin` starts the input observer, outside the grant's lock (check, act, check again), so the monitor, `Token`, `Require` and a revocation by the user's input no longer wait for a slow launch or hook installation. A grant revoked during a launch still returns what started (the caller owns closing it) and notes no target, and neither does a batch that began meanwhile; an observer started for a `Begin` that lost to another is disposed. Fixed offline 2026-11-10, not live-verified.
- Argument errors found before any input now carry `failure.code: invalid-arguments` instead of the generic `operation-failed`: `windows_send_keys` with neither or both of `chord` and `keys`, `windows_focus` without `handle` or `title`, `windows_close` without `handle`, and a `windows_batch` over 100 steps. Texts are unchanged. Fixed offline 2026-11-10, not live-verified.
- `windows_type`, `windows_send_keys` and `windows_paste` resolve their target (ref, window handle or foreground) through one shared resolver. A window handle whose process is off the app allowlist is now refused with the typed `failure.code: process-not-allowed` (`not-dispatched`, `actionDispatched: false`), as the foreground path already was; it used to surface as `operation-failed`. The text is unchanged. Fixed offline 2026-11-10, not live-verified.
- `windows_type` with a ref and no `verifyFocus` reads the ref's keyboard focus before the keys and names the ref in its reply only when it held focus; otherwise the text is `Typed "…"; focus on <ref> was not verified, so the text went wherever keyboard focus was. Observe before continuing.` Status (`unverified`) and the default (`verifyFocus` false) are unchanged. Fixed offline 2026-11-10, not live-verified.
- `windows_paste` whose read-back finds the value unchanged but already holding the text reports `proof.verdict: unchanged` and `status: unverified`, where it was `no-op` and `ok`: an unchanged value does not show that Ctrl+V reached the ref. `verification: unchanged` is as before. Fixed offline 2026-11-10, not live-verified.
- A `windows_mouse` drag that breaks off and lets go of the button stays `unverified` (`drag-interrupted` or `drop-target-moved`), so a held grant carries on. Only when the release itself did not go out, so the button may still be held, is the call `status: failed`, `dispatch: partial` and `isError: true` with the text `Failed to drag: …`; the registry's failed-after-input hooks then fire and a host pauses its grant. That case is `drag-interrupted` even after a moved drop target (it was `drop-target-moved`, `unverified`). Fixed offline 2026-11-10, not live-verified.
- A `windows_mouse` drag reads the pointer again right before the press and right before the release, after the slow re-checks, and moves it back to the proved point when a tolerated physical nudge shifted it more than 2 px (a counted pointer move, no revocation), trying up to three times 20 ms apart. Only a pointer that is still more than 2 px off after that is refused: before the press with the new code `pointer-moved` (`actionDispatched: true`, the button never went down); with the button down it ends as `drag-interrupted (pointer-moved)` with Escape and the release. Fixed offline 2026-11-10, not live-verified.
- `GrantRevocation.Summary()` words a normal end as "grant ended (…, end)" and input after one as "input after a normal end (…, after-end)"; only a revocation reads "grant revoked". Reason texts and refusal codes are unchanged.
- `InteractionGrant.LastRevocation` is no longer replaced by an `End()` that finds no batch active (the grant was already revoked), so ending after a revocation keeps its evidence. The user's input after a normal end, which still stops safety consumers such as a recording, is recorded with the new cause `after-end` instead of `user-input`; `GrantRevocation.EndedNormally` is true for `end` and `after-end`.
- A deliberate loosening: the input observer tolerates tiny physical mouse drift (`MouseDriftFilter`). Only a physical `WM_MOUSEMOVE` may be tolerated, and only while the pointer stays within 20 px of the drift's anchor (10 px at first; it revoked a real nudge), however many events the motion is reported as (an event-count cap revoked a real hand nudge live, 2026-11-05). The anchor is the last move point of either source when a physical move follows a second of physical quiet; tolerated moves never move it, and any injected mouse event drops it. Nothing is tolerated within 500 ms of an injected mouse event or before a reference point exists. Keys, button downs and ups, wheels and any move past the radius still count at once. The number of tolerated moves (no coordinates) is `IInputEventSource.ToleratedMoves` and `GrantRevocation.ToleratedMoves` for the batch.
- An approved `InteractionGrant` batch holds the display and the system on (the existing `PowerAvailabilityRequest`, display and system required) from `Begin` until it ends, is revoked or the grant is disposed, so a display that times out between calls cannot end the batch on wake-up. Only a grant that watches the real input holds it, never under `FLAUI_OFFLINE_TESTS=1`; the new `keepDisplayOn` constructor seam replaces it in tests. A request that fails never blocks the grant; `DisplayRequestProblem` says why.
- The input observer restarts its heartbeat clock just before it installs its hooks, so a slow thread start no longer poisons it at birth; slow hook installation still does.
- `InteractionGrant.LastRevocation` (`GrantRevocation`) keeps how the last grant ended: UTC time, code, reason, cause (`user-input`, `observer-fault`, `foreground`, `activation`, `host-stopped`, `end`), approved and snapshot sequences, the coinciding input kind with a mouse subtype (`InputEventInfo.MouseKind`: move, button, wheel) and, for an observer fault, an `ObserverFault` (heartbeat-gap, thread-exited or disposed; the gap at the latch and at the next beat, the GC pause in it, and whether Windows saw input in it). `Summary()` is one line for a host's diagnostics. The live observer now throws `ObserverUnavailableException` (an `InvalidOperationException`) carrying the fault; a fault also records the event that coincided with it. Reason texts and codes are unchanged.
- A settled tool failure with no recorded input and no specific refusal now carries `failure.code: operation-failed` and `actionDispatched: false`. Pending provider calls remain untyped; counted or otherwise known dispatched actions keep their dispatch evidence, including through batch rollups and grant observers when a provider reported dispatch without a counted input.

### Shared Core

The generic `windows_*` changes are recorded in the [Core changelog](https://github.com/eugman/FlaUI-MCP-Core/blob/main/CHANGELOG.md).

### Added
- `te3_layout` on the TE3 companion server arranges TE3 for a screenshot. `close` and `keep` hide docked panes by title (document tabs are never closed), and stop at a dialog such as a save prompt. `maximize-pane` and `restore-pane` use the pane's own buttons. `resize` drags the dock splitter until a pane is a given width or height, and reports the size reached. Pane titles match with or without TE3's " (Changed)" suffix. `te3_layout_read` lists docked panes and document tabs with bounds.

### Fixed
- `te3_native_preflight` follows `nextCursor` in `tools/list` (up to 20 pages), so an identity tool on a later page is found instead of reported unavailable.
- `te3_layout resize` and `apply-preset` read the pane after a drag until two reads 100 ms apart agree (up to 1.5 s) instead of once after a fixed 300 ms, so a slow re-layout is not reported as a miss that pauses the grant.
- The runner's model checks after TE3's Save (Ctrl+S, no read-back) no longer read once and believe it (`PersistedCheck`, on an injected clock). `Query` and `Metadata` read again, for up to 10 s, only when the model was read and still holds another value; a failed TE CLI call or a result of the wrong shape fails at once. `Unchanged` confirms an unchanged read with one more read a second later, so a save that lands late is not passed as unchanged.
- `te3_layout keep` no longer reports a verified proof with panes still open: any docked or floating pane that should have closed and is still present is listed in `unresolved`, and `closed` (for `close` too) holds only panes the read-back found gone, not every pane whose Close was pressed. Keeping a document tab or a floating pane no longer reports a false mismatch; a kept title counts as present wherever it is shown.
- After the user's input revokes a run's grant, the run still ends the TE3 it launched and restores the preferences. It kills that TE3 without a close request, because TE3 answers a close on a model with unsaved edits with a save prompt on the desktop the user has just taken back; a run that ends with its grant still asks TE3 to close and kills it only when the close is not posted or not obeyed. Neither asks the grant; each is sent only straight after the process is verified as the run's own (PID, start time, executable). `actions.jsonl` records whether the close message was posted and a `te3_kill` entry with its reason, and the manifest's `diagnosticNotes` say which happened. Every other input is still refused. Before, the close was refused, TE3 stayed open with normalized settings and the run needed `recover --force`. The run's cleanup is now `RunCleanup`, tested on a scripted process.
- A run, and `recover`, remove the settings backup folder (`fla_settings_<guid>` under `%LOCALAPPDATA%/FlaUI-MCP/settings-backups`) once the restore is hash-verified and the run's manifest no longer needs recovery; before, every run left one behind. The backup is kept on a checksum mismatch, a partial restore, an interrupted run or an unmarked manifest. `recover` reports `backupRetained` and says so plainly when the backup is already gone. Backups left by earlier versions are not swept.
- `te3_navigate` works when TOM Explorer is a docked pane rather than a tab.
- `te3_navigate` destination `object` picks among rows that share a name (a table, a column and a hierarchy level all called "Date") by the property grid's Object Type. It selects candidates through `windows_click`'s select path, so it never clicks a row that is already selected, which would start an inline rename.
- Engine recipes reset `fixedSlot` to the test model before each recipe. They save into the shared database, so a run of several recipes (or `--repeat`) failed from the second recipe on with a misleading "pass folder" error.
- `te3_model_state` reports a minimized TE3 instead of "Expected one element; found 0": a minimized TE3 leaves its status bar out of the UI Automation tree.
- A local recipe that reuses a recipe id is reported by name.
- The object-not-found message no longer implies the object is in a display folder.

### Changed
- The repo builds on the shared FlaUI-MCP-Core and takes its changes by merge. The host project is now `FlaUI.Mcp.Te3` (was `FlaUI.Automation`).
- Personal documentation recipes, run configs, the screenshot backlog, the SpaceParts fixture and the agent study live in a gitignored `local/` folder. The runner compiles `local/recipes` when it exists; the repo ships the eight smoke recipes.
- `te3_navigate` and `te3_model_state` find the running TE3 when `processId` is omitted or null, and ask for it only when several are open.
- `automation/reset-engine.ps1` creates (`-Create`) and resets the `fla_te3_small` database that engine recipes use.
- The `te3-ui` skill ships the composed TE3 guidance instead of an empty placeholder. Docs are consolidated into `automation/README.md`, `UI-MAP.md` and `KNOWN-ISSUES.md`.

### Added
- `te3_model_state` on the TE3 companion server: a read-only status-bar observation reporting load state, Best Practice Analyzer count, caret position, selected object and connection state. Takes no desktop focus and sends no input. A status bar that does not match the observed shape — wrong panel count, or panels that collide when mapped — is reported as unrecognized rather than mapped on a guess. "Recognized" means those checks held, not that the layout is proven.

### Fixed
- A run no longer needs manual recovery because TE3 rewrote a file nothing restores. `SettingsChanges` hashes every file in the TE3 settings folder while `SettingsLease` restores four, so ordinary launch churn (MRU lists, session state, caches) marked the run `NeedsRecovery` — which `ArtifactFiles.Promote` refuses outright, blocking every capture from it with no action that could clear it. Only a leased file left changed is a recovery condition; the rest are warnings, surfaced in `index.html`.
- `Unchanged()` compares the persisted model *before* saving on top of it, so a recipe that mutated the fixture is reported rather than having the mutation committed and then reported. The in-memory path still flushes with Ctrl+S to see an unsaved edit, which the code says plainly.
- `ParkPoint` clamps to both edges of the window. Clamping only the lower bound put the pointer one pixel above a zero-height rectangle, failing the obscured check it was added to avoid; a rectangle with no interior is now refused outright.
- Backlog promotion could publish the clean capture of an item that needs redaction. The requirement lived only in prose, while the About dialog shows the licence holder, installations and session id. Items now carry `requiresRedaction`, every identity-revealing item sets it, and the check lives in `ArtifactFiles.Promote` itself, so the raw `promote <run> <item> <path>` command line cannot bypass it either.
